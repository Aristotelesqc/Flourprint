# Review PR #133 @ e7aaad3 (read-only)

Scope read: docs/mockups/0.3-ux/src (model, preparation-runtime, PreparationView, ProcessView, RecipeView, RecipeHistory, DependencyEditor), packages/ui (tokens, number-field, sortable-list, tests), core contracts (bake-session.md L150-300, requirements L111/L127), core bake/process APIs, adapters/memory recipe repository. Not exhaustively read: the 1.5k-line views end to end, the 30 Playwright specs, packages/ui CSS. Nothing was run. The diff touches no file under apps/ or packages/core (scope respected).

Verdict: no blocker, but NOT a faithful client yet. The engine calls themselves are mostly right (Next = CompleteStep only; previousAction; implicitStartOf then StartStep; adjustedDurationS; heldSeconds; visibleEvents; outcomeChoiceRequired). The problems are around them: swallowed refusals, a parallel session model, notes outside the engine, and process edits that skip core edit helpers.

Counts: blocker 0, major 6, minor 11, nit 4.

## Major

M1. Notes and photos bypass the engine. PreparationView.tsx:1404-1407 calls store.log, model.ts:959-960 writes session.journal (mockup-only), and updateSession (model.ts:722) refuses finished sessions. The contract says a note is AddObservation (free text) and is allowed after the end (bake-session.md ~L275: "Ordinary notes may target any step, in any state, during or after the bake"). Failure: a note typed during a bake is not in the event log, so it is not exported or replayed, and a post-bake review note is impossible. The journal then merges the two sources with a (at,text) de-dup hack (PreparationView.tsx:628-638), and BakeStarted is shown twice, once from the seeded journal and once from the event.

M2. Engine refusals are swallowed or flattened. Results of executeBakeCommand are ignored in handleRetractStep (PreparationView.tsx:350-353), handlePauseToggle (385-392), handleAdjust (399-408), the doughReady button (835-848) and the preheat Start/Ready buttons (897-914). Pause is not gated on "has a planned duration / not beforeTarget" (contract: InvalidCommand), so on a model-driven step the button silently does nothing. handleNext (306-340) maps 5 codes to canned copy and everything else to errorGenericCommand, dropping the engine reason. Other dialogs print res.bakeError.message (raw English engine text, 1462) or the raw code (`?? res.bakeError?.code`, 457, 1435). Failure: tap Pause on a step with no duration; nothing happens and no reason is shown.

M3. +15 min fabricates a duration. handleAdjust (PreparationView.tsx:397) uses `plannedDurationS ?? 0`, so +15 on a step whose duration is unknown (model-driven) records AdjustStep plannedDurationS=900. Only -15 is disabled (717). This breaks L15 (unknown is never zero) and also formatStepAdjustment (preparation-runtime.ts:51-52, `?? 0`).

M4. A second, mockup-only session model duplicates persisted state. Session (model.ts:68-86) keeps facts, effective, activeId, startedAt, finished, abandoned, endedAt, outcome, outcomeSource, journal, checks next to engineRuntime, and sessionHistory stores clones. activeId is derived by local graph logic (model.ts:898-912: first unended step whose deps ended, in list order), which is not strand-aware (L127: Next never advances a parallel branch; contract: "UI passes the step of the strand it shows") and cannot be rebuilt from events after a reload. engineRuntime is optional, with a second non-engine path (finishSession model.ts:826-845 using intendedOutcome/outcomeProblem; lazy engine creation at 845-860). preparation-runtime.ts:67-143 rewrites the application use case (executeBakeCommand in packages/core/src/application/bake.ts:66): causationId = payload.type, no commandId/idempotency/expectedVersion. Port impact: apps/mobile would have to rip out Session and use the application use case with ports; the mockup would be better built on it with an in-memory store.

M5. Process edits skip the core edit helpers. StepEditor apply (ProcessView.tsx:1467-1473), dependency edit (1503-1509), DependencyEditor.tsx:30-60 (its own candidate filtering with validateProcess) splice objects by hand. apps/mobile uses updateStep (StepSheet.tsx:169), which the mockup never imports. Remove uses removeStep and ignores the result (1586), though removeStepChecked exists (TargetInUse), and then announces "changeApplied" unconditionally (1587-1588). applyProcess (model.ts:448-456) re-validates locally and maps every refusal to the move message `refusedMove`, even for non-move edits. Failure: remove the step that a preheat targets; the user is told the change was applied while the process may be refused or inconsistent.

M6. History/restore/promote rules are re-implemented in the mockup (model.ts:~985-1100) instead of mirroring the repository contract (packages/adapters/src/memory/recipe-repository.ts:90-160). Guard order differs (mockup: trashed, head, existence; repository: trashed, existence, head), so a stale head plus an unknown revision gives a different error. Numbering differs (max+1 vs list.length+1). Restore copies name/names, the repository copies note. RecipeHistory.tsx:36-37 predicts the next number in the UI, and 53-58/70 cast store functions with `as` to a different signature (type escape). Acceptable only if labelled; as it stands the mockup "validates" rules that may drift.

## Minor

m1. Local domain arithmetic and rounding: RecipeView.tsx:380/423 water share = grams/positiveSum*100 (shares can sum to 99.9 or 100.1; core already has the contributions); RecipeView.tsx:871-872 anchor switch invents count: 2 and Math.round(doughWeight/2) / Math.round(doughWeight), which changes the total dough weight (formula.md:129 expects the value of the new anchor from the baker); RecipeView.tsx final group `mass: sum(rows...)` while the comment claims "never a second UI solver".
m2. Preparation timing is re-derived (PreparationView.tsx:226-243): elapsed, remaining, progress, overdue, `elapsedOffsetS` (always 0, dead). formatCountdownHHMMSS floors, formatStepAdjustment uses Math.round of minutes (preparation-runtime.ts:54) with a hard-coded "min"; a 7m30 adjustment reads "+8 min". Prefer one core projection value plus one shared formatter.
m3. "Previous" target is chosen locally (PreparationView.tsx:~262-282, subject/dependsOn heuristic). Core gives previousAction(stepId) but not the strand choice; document it or add a core helper.
m4. finishSession(chosenOutcome): chosenOutcome is component state not tied to the session; a stale choice survives after more steps are completed (needsChoice flips) and is sent as an override even when equal to the default (PreparationView.tsx:418, 1212). Every finish path does go through needsChoice (good).
m5. Hard-coded text: 'reprise'/'repetition' stored in the step label (PreparationView.tsx:445, locale baked into data); 'No active session' (model.ts:842); unit="min" (PreparationView.tsx:1080, 1125, 1469; ProcessView.tsx:244); `' : '` colon logic by locale in DependencyEditor.tsx:71. Copy is split across ~14 *-copy.ts files besides messages.ts; hard to port. FR copy has no tu/vous in what I scanned; EN present everywhere because entries are [fr,en] tuples.
m6. Internal codes shown: ObservationAdded falls back to the raw category (`fermentation`, `handling`) (PreparationView.tsx:578-581); engine messages shown raw (see M2).
m7. Weighing (L111): recipe -> preparation carry-over and reset are implemented (model.ts:~690-710), but Planning has no weighing checks at all (ProcessView has none) although L111 says Planning shares them. Check keys are `component:ingredient` row keys built from the resolved view (RecipeView.tsx:79-137): a rename or a zero-gram row appearing makes them stale. The state (Recipe.checks map, Session.checks) is in no persistence contract (drafts.md "recipe checks" is validation, not weighing); flag as a port decision.
m8. History: "No rating" is shown for every finished preparation (RecipeHistory.tsx:~308) although no rating can be recorded in the UI (invented absence); duration is endedAt-startedAt where endedAt is set to `now` in mockup state, not read from the event. Combining active + past sessions and no invented outcomes: OK.

Hard-coded colours with fallbacks in app/mockup code: `var(--fp-color-error, #ba1a1a)` etc. (PreparationView.tsx:780, 796, 1073, 1118, 1462; DependencyEditor.tsx:96; RecipeView.tsx:305-312, 375-487), raw `#9c4174` / `#5b631e` chart colours (RecipeView.tsx:311-312), inline styles (91 in the mockup).
