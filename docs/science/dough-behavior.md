# Fermented dough behavior: scientific state and product traceability

This is the entry point for what Flourprint knows, assumes, has chosen to model or leave out,
computes, shows to the baker and has delivered, for the behavior of fermented dough from the mix
to the oven. It connects four things that are easy to confuse: the evidence
([fermentation-model.md](fermentation-model.md), [sources.md](sources.md), `data/`, `scripts/`),
the contracts (`docs/contracts/`, what the program must do), the code and the screens, and the
pull requests that carry them. It does not repeat the research reports and it changes no model.

**Scope.** Microbial activity and substrate, fermentation heat, gas production and retention,
evolving dough structure, water availability, physical expansion, mechanical operations,
readiness, and the changes up to baking. Oven and cooking physics stay with issue #28 and
[equipment.md](../contracts/equipment.md); only their interface with fermented dough appears here,
as links.

**What this file is not.** It is not a model change, not a contract, not a promise that every
domain will be implemented, and not a claim that any simulation is experimentally validated. A
domain with no science, no contract and no code is listed as such. An absent issue is not a
defect, an absent line of code is not a rejected idea, and "not inspected" is never "not
implemented".

**A maintained map, not an audit report.** Reports are not committed to the repository
(AGENTS.md); this document is a living map that later pull requests keep current under the
maintenance rule at the end. "Known inconsistencies" is likewise a living list: each later pull
request that resolves one removes it, and the list is meant to be emptied over time.

## How this file relates to the behavior model

This file maps every domain of fermented dough, timing included. The foundations of the behavior
model (how a dough handles and what it becomes, as opposed to when it is ready) are proposals in
[behavior-model-foundations.md](behavior-model-foundations.md), which maps the domains below to
timing, behavior or both. The behavior model has no contract, code or screen: its place in this
map is domain 14 and, for the formula and process drivers, domains 6b, 7, 8 and 12b.

## Status vocabulary

| Dimension                | Words used                                                                                                                    |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Scientific documentation | `not documented`, `partial`, `documented`                                                                                     |
| Contract                 | `none`, `proposed`, `provisional`, `approved`, `draft for Alpha` (the contract's own words are quoted)                        |
| Conformance and backend  | `not implemented`, `partial`, `implemented`, `unverified`, `N/A`; backend adds `stored` (kept, never read)                    |
| Frontend                 | `not exposed`, `mockup`, `UI only` (a field exists, no model reads it), `wired`, `verified` (a test in the tree exercises it) |
| Validation               | `assumed`, `fitted`, `measured`, `independently tested`, `not validated`; software evidence is named apart                    |
| Decision                 | `selected`, `simplified`, `deferred`, `rejected`, `undecided / no recorded decision`                                          |

A cell may add a short qualifier in parentheses; the qualifier does not replace the status word.

Evidence labels are those of [README.md](README.md#provenance-labels) (MEASURED, DERIVED / FITTED,
ASSUMED, EXTRAPOLATED, MODEL OUTPUT) and read status is a separate field. The authority for
classifying a source (reading, reason for an incomplete reading, soundness, scope, role,
workarounds) is [evidence-classification.md](evidence-classification.md), applied in
[sources.md](sources.md#classification-of-evidence); practitioner claims are graded apart in
[craft-knowledge.md](craft-knowledge.md) and never calibrate or validate a coefficient.

**Authority tags used in dimension 10.**

| Tag     | Meaning                                                                                                                                                       |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OD      | Owner decision, dated, with the place it is written (issue comment, PR, contract, ledger).                                                                    |
| OD-chat | Owner decision made "in session with the coordinating agent" on the given date and relayed; not yet written elsewhere in the repository.                      |
| ADR     | Accepted ADR, with its number. A proposed ADR is not authority.                                                                                               |
| CT      | Text merged in a contract on `dev`, with the contract's own status quoted when it is not "approved". A contract is not proof that the owner chose the detail. |
| LEDGER  | Item of the requirements ledger [docs/ux/requirements.md](../ux/requirements.md).                                                                             |
| SCI     | A position stated in a science document written by an agent. The owner's approval is the merge, nothing more.                                                 |
| ISSUE   | A requirement written in an issue body or comment.                                                                                                            |
| AG      | An agent or external-report proposal. Not a project decision.                                                                                                 |

"Rejected" is written only where an alternative was actually compared and declined by an owner
statement, a contract or an ADR. A conclusion of a science document that an approach is not
supported by the data is called "not supported by the evidence (SCI)", which is not a project
rejection.

<a id="d03-co2-production-retention-and-volume"></a>

### 3. CO2 production, dissolution, retention, venting, bubbles, visible height and volume

1. **Domain.** Gas production versus retention versus visible height or volume; bubble nucleation, growth and coalescence.
2. **Science.** `partial`. fm section 3 (four end points that cannot be converted into each other); Covino's slow start with its three unseparated hypotheses (fm section 5); Timmermans (3-hour CO2, sugar), Boudrag and Belz (salt: production versus retained gas), fm sections 6 and 8; Birch's height-fit parameter is "not a CO2 constant"; the height-ceiling hypothesis is a candidate (fm section 12). Verheyen 2014 and 2015 (Rheofermentometer, 30 C, read in full through the thesis): production and retention separate: at equal dry-matter dose compressed and instant dry yeast produce a total CO2 of the same size in 180 min (the printed intervals overlap at 6 of 8 doses; the two that do not differ by 60 and 70 ml, 5 to 6 %, with no significance test; the authors call the totals "similar" and about 1500 ml "identical"), but the CO2 held at the time of gas escape falls with the gas rate for compressed yeast (minimum 372 ml per 315 g dough) and stays at 538 to 564 ml for instant dry yeast; domain 0.25 to 3.0 g dry matter per 100 g flour, one flour, no cold (data/verheyen-2015.md). Stanke 2014 abstract, Paquet-Durand 2020 (online estimation, not forecasting). Gas-assay method evidence is limited to what was read: the Risograph measures evolved gas, not height or readiness (McKinnon 1996 Fig. 2, full text, sources.md); Rattin 2009, the Risograph method paper retained at the owner's request, read in full on 2026-11-13 (UTC) from a page-image copy (sources.md): the gas measured per gram of dough rises with the time between mixing and measurement, so gas assays are comparable only at equal bench time. ## Maintenance rule

A pull request or an approved decision that materially changes a domain's science, an
architectural or ADR choice, a deliberate scope, a contract, the engine, or the UI or delivery
status updates the matching subsection in the same pull request, or says in its description why it
does not. Update the "As of" table when the refs are re-checked. When a row changes, keep the
superseded position and its date (strike it into a short "was ..." clause) rather than erasing it,
and keep the new position's authority tag. A PR that touches none of these needs nothing.

Dimension 10 changes only on an actual decision (owner statement, accepted ADR, merged
contract with owner approval), never because code was or was not written. When an ADR is
proposed, accepted, amended or superseded, review the rows that cite it and do not assume they
changed. Do not transcribe source tables here: link the `data/` file.
